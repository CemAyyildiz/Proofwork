Sealed dual review (experimental)
=================================

Proofwork can optionally bind one pending submission to exactly two reviewers: the configured founder wallet and the campaign's original creator wallet. A Sub Rosa Core v2 ReceiptOnly round keeps their independent rubric v2 assessments sealed until a shared Drand reveal boundary. The feature is additive and off by default.

Enable on a preview deployment
------------------------------

1. Create a Neon preview branch; do not point this branch at the production database.
2. Set DATABASE_URL to the preview branch and run `corepack pnpm db:migrate`.
3. Set SEALED_DUAL_REVIEW_ENABLED=true and SEALED_REVIEW_ADMIN_PUBKEY to the founder's external wallet. The public key must not match any backend-held signing key.
4. Deploy the preview. Create a new campaign and select Founder-sealed review before its escrow is deployed.
5. Fund that new escrow, then connect the campaign creator wallet at /review/sealed and open the round. There are no reviewer address fields: Proofwork derives the pair from trusted configuration and the immutable campaign creator.

Migrations 0007 and 0008 add the sealed review tables and replay protection. Migration 0009 adds a founder-sealed flag and the escrow release-signer public key to campaigns. Both default to the legacy behavior, so existing campaigns and deployed escrows are not rewritten.

Lifecycle and trust boundary
----------------------------

- Only the original campaign creator can prepare and create the round. Proofwork derives the exact allowlist as [configured founder, original campaign creator] and rejects a same-wallet pair.
- The campaign creator creates the round through the published @sub-rosa/sdk@0.3.2. It is pinned to Stellar testnet, the SDK's canonical Core v2 contract, ReceiptOnly, those two allowlisted participants, and fixed escrow 0.
- Each assigned reviewer signs its own Soroban commit. Proofwork receives only the transaction hash and verifies the resulting on-chain commitment before recording it.
- Before reveal, Proofwork stores no assessment signals, reason, note, plaintext envelope, ciphertext, nonce, or wallet secret. The ciphertext lives in Sub Rosa temporary contract storage.
- Core v2 permits a participant to overwrite its own sealed payload before the commit deadline. Proofwork pins the first commitment it records and rejects a reveal or receipt if the final on-chain commitment differs. The UI also removes the commit action after the first accepted commit.
- After Drand publishes the configured round, reveal is permissionless to open. Each assigned reviewer decrypts and reveals its own payload. Clearing is allowed only after the reveal deadline; for ReceiptOnly, clearV2 finalizes the contract state directly to Settled.
- Proofwork exports the receipt from on-chain state, calls verifyReceiptV2, checks the contract/network/mode/zero-escrow policy, exact allowlist, item and schema references, deadlines, operator, reviewer commitments, and every embedded Proofwork binding. Only then are the two plaintext assessments stored and displayed.
- Only the configured founder wallet can select one verified assessment as the final human decision. The ordinary review queue and decision endpoint reject founder-sealed submissions. Finalization calls the existing ledger path with a verified-round capability and writes exactly one normal Proofwork decision-ledger record.

Sub Rosa does not custody USDC or call Trustless Work. For a newly created compatible campaign, Proofwork deploys Trustless Work with the campaign creator as funder/remainder recipient, platform ops as approver, and the external founder wallet as releaseSigner. After a receipt-verified founder PASS, only that founder session can request milestone approval and only that founder wallet can sign the release XDR. The backend holds no founder secret. The creator cannot release a reward directly on chain, but remains able to close the campaign through the existing dispute/remainder path. Existing funded escrows and all single-review campaigns retain their original roles and behavior.

Privacy and operational limits
------------------------------

This is timed confidentiality, not permanent confidentiality. Anyone who obtains the ciphertext can decrypt it after the Drand boundary, and revealed payloads are public on-chain. Notes and rubric signals are intentionally stored by Proofwork only after receipt verification. Transaction hashes, reviewer wallet addresses, commitments, timing, and the public Proofwork item binding are visible before reveal.

If fewer than two valid reveals are recorded by the deadline, Proofwork marks the integration round expired and refuses finalization. If the Sub Rosa temporary seal expires before reveal, the review cannot be recovered through the normal path. A contract transaction that succeeds but whose acknowledgement never reaches Proofwork must be reconciled from the on-chain receipt; server responses never include assessment plaintext before reveal.

Reproduce the live proof
------------------------

Run `corepack pnpm test:sealed-review:testnet`.

The harness creates three fresh testnet accounts (founder, campaign creator, and unauthorized outsider), funds only their XLM fees with Friendbot, has the creator open a real round for the fixed founder/creator pair, submits their two zero-escrow sealed assessments, checks pre-reveal privacy and outsider rejection, waits for timed reveal, reveals both in parallel, clears, verifies the canonical receipt and Proofwork bindings, and prints evidence JSON. It uses no mainnet account, token, USDC, Trustless Work call, or application secret.

The Trustless Work authorization model is additionally covered by adapter/service tests: a founder-sealed deployment records the external founder as releaseSigner; creator and unrelated payout requests are refused; and a direct creator-signed release attempted against the escrow model fails before the founder-signed release succeeds. A live Trustless Work testnet run requires TW_API_KEY plus a funded testnet-USDC account and must never target a production escrow.

The committed run is recorded in docs/evidence/sub-rosa-sealed-dual-review-testnet.json.
